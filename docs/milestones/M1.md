# M1 — 기반 + 회원 + 상품

> 마일스톤은 **기능 목록이 아니라 완료 조건**이다.
> 이 문서의 진짜 목적은 "이번에 하지 않을 것"을 정하는 데 있다.

---

## 완료 조건

아래가 전부 동작하면 M1은 끝이다. 논쟁의 여지가 없어야 한다.

- [ ] 사용자가 이메일·비밀번호로 가입하고, 휴대폰 인증을 거쳐, 닉네임을 정하고 계정을 만들 수 있다
- [ ] 가입한 사용자가 로그인·로그아웃할 수 있다
- [ ] 휴대폰 번호로 이메일을 찾을 수 있고, 결과가 마스킹되어 보인다
- [ ] 이메일로 비밀번호를 재설정할 수 있고, 같은 링크를 두 번 쓸 수 없다
- [ ] 사용자가 강북구 행정동 중 최대 2개를 내 동네로 등록하고 전환할 수 있다
- [ ] 사용자가 이미지를 올려 상품을 등록할 수 있고, 활성 동네로 자동 지정된다
- [ ] 활성 동네의 상품 목록을 보고, 검색·정렬·페이지 이동을 할 수 있다
- [ ] 상품 상세에서 판매자 정보와 그 판매자의 다른 상품을 볼 수 있다
- [ ] 본인 상품만 수정·삭제할 수 있다. 타인이 시도하면 403이 반환된다
- [ ] 거래완료 상품은 수정할 수 없다
- [ ] 삭제한 상품이 목록에서 사라지지만 DB에는 남아 있다
- [ ] 위 흐름이 **REST(api 모듈)와 SSR(web 모듈) 양쪽에서** 동작한다
- [ ] 위 흐름이 통합 테스트로 검증된다
- [ ] dev 프로필에서 mock 상품 20만 건을 적재할 수 있다

## 이번에 하지 않는 것

**기능**: 채팅, 거래(예약·구매확정), AI 상품 등록, 알림, 결제, 마이페이지, 범위 설정, 소셜 로그인, 탈퇴, 끌어올리기

**인프라**: Redis, Kafka, Elasticsearch, S3, Docker 배포, Jenkins

**최적화**: N+1 해결, 인덱스 생성, 커서 페이징, 캐싱

**프론트엔드**: React SPA (M3)

**외부 연동**: 실제 SMS 발송, 실제 메일 발송 — 인터페이스만 만들고 콘솔 출력

---

## 왜 최적화를 하지 않나

M1의 목록 조회는 **일부러 느리게 둔다.** N+1이 나고, 인덱스가 없고, `OFFSET` 페이징이다.

이 프로젝트의 원칙이 "가벼운 대안 먼저 → 한계 측정 → 교체"이기 때문이다.
처음부터 최적화하면 before/after 비교가 성립하지 않고, 무엇이 왜 느렸는지도 알 수 없다.

**전역 지침(`~/.claude/CLAUDE.md`)의 "N+1 점검" 규칙은 M1에서 적용하지 않는다.**
→ 프로젝트 `CLAUDE.md`의 예외 블록 참조

## 작업 순서

### 0단계 — 프로젝트 골격

- [x] Gradle 멀티모듈 구성 (`core` / `api` / `web`)
- [x] `core`는 `bootJar` 비활성, `jar`만 생성
- [x] `api`, `web`은 각각 `core`만 의존. 서로 모름
- [x] 패키지를 `com.golmok`으로 통일 (컴포넌트 스캔 문제 회피)
- [x] PostgreSQL docker-compose
- [ ] Flyway 설정, 프로필 분리 (`db/migration`, `db/dev`)
      → `classpath:db/migration`만 설정. `db/dev` 분리는 넣을 mock이 생기는 **4단계**에서
- [x] ArchUnit 규칙: `core`는 `api`/`web`을 참조하지 않는다
- [x] GitHub Actions CI (`main`/`develop` push + PR에서 `./gradlew build`)

## 스코프가 부풀 때

마감이 없는 프로젝트에서 가장 큰 위험은 "새로 짜는 김에"다.
아래가 떠오르면 **M2로 미룬다.**

- "이미지 올리는 김에 S3도"
- "목록 만드는 김에 인덱스도"
- "화면 만드는 김에 반응형도"
- "인증 만드는 김에 소셜도"

M1은 초라해 보이는 게 정상이다. 앞으로 쌓아 올릴 바닥을 까는 작업이다.
