# 0007. PK는 identity 컬럼으로 생성한다

- 상태: 채택
- 날짜: 2026-09-09

## 맥락

`region`이 이 저장소의 첫 테이블이다. 여기서 정한 id 생성 방식이 이후 모든 테이블과
엔티티의 `@GeneratedValue` 전략을 결정한다. `decisions/0006`의 동결 규칙 때문에
M1이 끝나면 되돌리기 어렵다.

`docs/spec/`은 `bigint id PK`라는 타입만 정하고 생성 방식은 정하지 않았다.

세 가지를 검토했다.

- (A) `bigint GENERATED BY DEFAULT AS IDENTITY`
- (B) `bigserial`
- (C) 테이블별 시퀀스 + `@GeneratedValue(SEQUENCE)` + `allocationSize`

## 결정

(A)를 택한다.

```sql
id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

엔티티는 `@GeneratedValue(strategy = GenerationType.IDENTITY)`로 맞춘다.

## 근거

**(B)를 버린 이유**: `bigserial`은 PostgreSQL 10 이전의 관행이다. 동작은 (A)와 거의 같지만
비표준이고, 시퀀스가 컬럼에 느슨하게 묶여 있어 `ALTER TABLE ... DROP COLUMN` 같은 작업에서
시퀀스가 남는다. identity 컬럼은 SQL 표준이고 소유권이 명확하다.

**`GENERATED ALWAYS`가 아니라 `BY DEFAULT`인 이유**: `ALWAYS`는 명시적 id INSERT를 막는다.
테스트 픽스처나 데이터 보정에서 id를 지정해야 할 때 `OVERRIDING SYSTEM VALUE`를 매번 붙여야 한다.
얻는 안전성에 비해 번거롭다.

**(C)를 버린 이유와 그 대가**: (C)의 장점은 Hibernate가 INSERT를 배치로 묶을 수 있다는 것이다.
`IDENTITY`는 INSERT마다 생성된 키를 돌려받아야 해서 Hibernate가 JDBC 배치를 쓸 수 없다.

**이 단점을 M1에서 감수하는 이유**는 대량 쓰기 경로가 Hibernate를 거치지 않기 때문이다.
mock 상품 20만 건은 `generate_series` 기반 SQL 스크립트로 넣는다(`decisions/0006`).
애플리케이션이 하는 INSERT는 상품 등록·회원 가입처럼 건당 1행이라 배치가 의미 없다.

대신 id가 드문드문 비지 않고, 테이블마다 시퀀스를 관리할 필요가 없다.

## 결과

- 기준 데이터(행정동 13건)를 넣을 때 **id를 명시하지 않는다.** identity가 부여하게 둔다.
  `BY DEFAULT`에 명시적 id를 넣으면 시퀀스가 전진하지 않아 이후 INSERT가 PK 충돌을 낸다
- 이 가정이 깨지는 시점 — **애플리케이션이 Hibernate로 대량 INSERT를 해야 할 때** — 에
  (C)를 재검토한다. 그때는 측정값을 근거로 남기고 새 ADR을 쓴다
