# 0002. LangGraph/FastAPI 대신 Spring AI

- 상태: 채택
- 날짜: 2026-09-09

## 맥락

이전 프로젝트는 AI 파이프라인을 Python/LangGraph + FastAPI로 분리하고
Spring Boot가 내부 API로 호출하는 구조였다. 분리의 근거는
"LangGraph/임베딩은 Python이 표준"이었다.

## 결정

Spring AI 2.0.1을 쓰고 별도 AI 서비스를 두지 않는다. AI는 `core`의 한 모듈이 된다.

- Spring Boot 4.0 (Spring Boot 3.x는 2026-06-30 EOL)
- Spring AI 2.0.1 (2.0.0 GA는 2026-06-12, 2.0.1은 2026-08-21 유지보수 릴리스)

## 근거

Python을 쓸 이유가 사라지면 서비스 분리의 근거도 사라진다.

기획서의 AI 파이프라인(이미지 분석 → 분류 → 유사상품 검색 → 가격 추정 → 텍스트 생성)은
조건 분기가 "분류 실패 시 재질문" 하나뿐인 **선형 파이프라인 + 재시도**다.
그래프 오케스트레이션의 진짜 값어치는 사이클, 휴먼 인 더 루프,
장기 실행 재개에서 나오는데 여기엔 없다.

직접 구현하는 쪽이 이득이기도 하다. 단계별 상태 + 재시도 + 부분 롤백은
나중에 만들 Saga 오케스트레이터와 구조가 같은 문제다.

## 결과

- 골든셋 평가 하네스를 JUnit으로 다시 만들어야 한다. 평가셋 자체는 그대로 옮겨간다
- 그래프가 필요해지면 LangGraph4j를 검토한다
- LLM 호출이 인프로세스가 되지만 Java 21 가상 스레드로 완화된다.
  병목은 커넥션 풀이나 API 레이트 리밋으로 옮겨갈 것으로 예상한다
- 나중에 AI를 다시 서비스로 분리한다면 **측정된 근거**를 갖고 한다
