# 0003. M1에서 N+1을 의도적으로 허용

- 상태: 채택 (M1 한정)
- 날짜: 2026-09-09

## 맥락

전역 지침(`~/.claude/CLAUDE.md`)에 "JPA 사용 시 N+1 문제 항상 점검
(fetch join, @EntityGraph, batch size 고려)" 규칙이 있다.

이 프로젝트의 원칙은 "가벼운 대안 먼저 → 한계 측정 → 교체"다.
상품 목록은 판매자 닉네임과 대표 이미지를 함께 보여주므로
소박하게 구현하면 N+1이 발생한다.

## 결정

**M1에서는 전역의 N+1 점검 규칙을 적용하지 않는다.**

목록 조회의 아래 항목을 의도적으로 최적화하지 않는다.

| 항목 | M1 | M2 |
|---|---|---|
| 판매자·이미지 조회 | N+1 발생 | fetch join / `@BatchSize` |
| 페이징 | `OFFSET` | 커서 방식 |
| 인덱스 | 없음 | `(region_id, status, deleted_at, created_at DESC)` |
| 검색 | `LIKE` | Elasticsearch |

## 근거

처음부터 최적화하면 before/after 비교가 성립하지 않는다.
무엇이 왜 느렸는지 모른 채 "좋다고 해서" 쓰게 된다.

mock 20만 건에서 실제로 느려지는 것을 측정한 뒤 개선하고,
그 수치를 `docs/measurements/`에 남긴다.

## 결과

- 프로젝트 `CLAUDE.md`에 예외를 명시한다.
  Claude Code가 fetch join을 먼저 제안하지 않도록 한다
- mock 데이터의 판매자를 수천 명 규모로 만든다.
  소수로 만들면 조인 캐시에 가려 N+1이 드러나지 않는다
- **M2에서 측정이 끝나면 이 예외를 해제한다**
