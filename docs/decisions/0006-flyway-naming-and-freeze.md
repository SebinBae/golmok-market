# 0006. Flyway 명명 규칙과 M1 종료 시 동결

- 상태: 채택
- 날짜: 2026-09-09

## 결정

**명명**: 타임스탬프 + 순번 + 사유

```
V20260909_01__create_product_table.sql
V20260909_02__add_region_to_product.sql
```

Flyway는 `_`를 버전 구분자로 보아 `20260909.01`로 파싱하므로 정렬이 정상이다.
순번을 붙이는 이유는 하루에 두 개를 만들 때 충돌을 피하기 위해서다.

**위치 분리**

| 경로 | 내용 | 프로필 |
|---|---|---|
| `db/migration` | 스키마 + 기준 데이터(행정동) | 전체 |
| `db/dev` | mock 사용자·상품 | dev만 |

**동결 시점**: M1 종료 시점부터 기존 마이그레이션을 수정하지 않는다.
이후 변경은 새 파일로만 추가한다.

## 근거

**타임스탬프 명명**: `V1`, `V2` 순번은 여러 브랜치에서 동시에 추가할 때 충돌한다.

**위치 분리**: Flyway 마이그레이션은 적용 후 체크섬이 고정되어 수정할 수 없다.
mock을 여기 넣으면 테스트 데이터를 바꿀 수 없게 되고, 배포 시 운영 DB에 들어간다.

**동결 시점을 M1 끝으로 잡은 이유**: 스키마가 흔들리는 개발 초기에
마이그레이션을 쌓으면 `create` → `add_column` → `rename_column`이 어지럽게 남는다.
그 시기에는 V1 하나를 고치고 DB를 날리는 편이 낫다.

동결 이후부터가 Flyway를 실제로 배우는 지점이다.
컬럼을 NOT NULL로 바꿀 때 기본값을 어떻게 채울지,
컬럼 이름을 무중단으로 어떻게 바꿀지 같은 문제를 겪게 된다.

## 결과

- mock 20만 건은 INSERT 나열이 아니라 `generate_series` 생성 스크립트로 작성한다.
  수십 MB 파일은 diff가 열리지 않고 클론이 느려진다
- 20건 프로필과 20만 건 프로필을 분리한다. 매번 20만 건을 적재하면 기동이 느려진다
