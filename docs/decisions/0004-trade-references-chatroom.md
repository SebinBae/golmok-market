# 0004. Trade는 Product를 직접 참조하지 않는다

- 상태: 채택
- 날짜: 2026-09-09

## 맥락

당근 방식을 확인한 결과:

1. 예약을 취소해도 채팅방은 남는다
2. 거래가 끝나면 채팅방이 닫힌다
3. **채팅 없이 바로 예약할 수 없다**

## 결정

```
Product  1 ─── N  ChatRoom
ChatRoom 1 ─── 0..1 Trade
```

`Trade`는 `ChatRoom`만 참조한다. 상품은 `chatRoom.product`로 따라간다.
`Product`와 `Trade` 사이에 직접 연결선을 두지 않는다.

엔티티 이름은 `Transaction`이 아니라 `Trade`다.
`@Transactional`, `TransactionManager`와 충돌해 코드를 읽을 때마다
어느 쪽인지 판단해야 하기 때문이다.

## 근거

3번 때문이다. 예약이 항상 채팅방에서 시작된다면,
Trade가 ChatRoom을 참조하는 구조가 **"채팅 없는 예약"을 구조적으로 불가능**하게 만든다.
규칙을 애플리케이션 검증이 아니라 스키마가 강제한다.

채팅방과 거래를 하나로 합치지 않은 이유는 수명이 다르기 때문이다.
채팅방은 예약보다 오래 살고(1), 거래 완료보다는 짧게 산다(2).
합치면 이 두 가지를 한 엔티티의 상태 전이로 표현해야 해서 엉킨다.

## 결과

- `ChatRoom`에 자체 상태(`OPEN`/`CLOSED`)가 필요하다. 파생값이 아니다
- **대가**: "상품당 활성 Trade는 하나"를 DB 유니크 인덱스로 바로 걸 수 없다.
  → 0005 참조
