# 화면 명세 (M1)

> 용어는 [glossary.md](./glossary.md), 엔티티는 [domain.md](./domain.md)를 따른다.
>
> **이 문서의 목적**: 화면에 무엇을 보여줄지가 곧 API 응답 DTO가 된다.
> "목록 카드에 판매자 닉네임을 보여준다"가 정해져야 응답에 닉네임을 담을지 정해지고,
> 그것이 조인이 필요한지 / N+1이 생기는지로 이어진다.

디자인 참조: Claude Design 산출물 (서비스명 "골목")

## 이동 경로

```
[비로그인]
  A1 로그인 ──(가입하기)──> A2 ──> A3 ──> A4 ──> R1 동네 선택 ──> P1
   │
   ├──(아이디를 잊음)──> A5 ──> A1
   └──(비밀번호를 잊음)──> A6 ──(메일 링크)──> A7 ──> A1

[로그인]
  P1 상품 목록 ─┬──> P2 상품 상세 ──(내 상품일 때)──> P4 수정
                ├──> P3 등록 ──> P2
                └──(동네 이름 탭)──> R2 내 동네 관리
```

**A4까지 끝나야 User를 INSERT한다.** 닉네임을 별도 단계로 분리했지만
`nickname`이 NOT NULL이므로, 그 전까지는 입력값을 세션에 들고 있다가 마지막에 한 번에 저장한다.

**R1은 가입 직후 필수 단계다.** 동네가 없으면 P1에서 보여줄 것이 없다.

## A1 — 로그인

**입력**: 이메일, 비밀번호

**검증**: 제출 시점에만 에러 표시. 표시 후에는 수정하는 즉시 사라짐

**주의**: 실패 메시지는 "이메일 또는 비밀번호가 올바르지 않습니다"로 통일한다.
"없는 이메일입니다"라고 알려주면 가입 여부를 알아내는 열거 공격이 가능해진다.

⚠️ **메시지 통일만으로는 부족하다.** 없는 이메일에서 해싱을 건너뛰면 응답이 62배 빨라져
시간만 재도 가입 여부가 드러난다. `LoginService`가 더미 해시로 비용을 맞춘다.
측정: `measurements/20260909-login-timing-enumeration.md`
어댑터에서 두 경우를 다른 상태코드·화면으로 처리하면 이 방어가 다시 무너진다.

## A2~A4 — 회원가입

### A2 이메일·비밀번호
- 이메일 형식 검증, 비밀번호 8자 이상, 비밀번호 확인 일치
- 이메일 중복 확인 → `UserCredential`의 `unique(provider, email) where provider='LOCAL'`

### A3 휴대폰 인증
- 번호 입력 → "인증번호 받기" → 코드 6자리 입력
- 화면에 필요한 것: **5분 만료 타이머**, 재발송 버튼, 코드 불일치 에러, 시도 횟수 초과 안내
- M1에서 실제 SMS는 발송하지 않고 **콘솔에 출력**한다 (`SmsSender` 인터페이스)
- 번호 중복 확인 → `users.phone_number` 부분 유니크

### A4 닉네임
- 2~20자. 중복 확인
- 추천 닉네임 칩을 눌러 채울 수 있음 (디자인 참조)
- **여기서 User + UserCredential을 INSERT한다**

---

## A5 — 아이디(이메일) 찾기

휴대폰 번호 입력 → 인증번호 → 결과

**결과는 반드시 마스킹한다**: `hy****@gmail.com`

가리지 않으면 번호를 무작위로 넣어 가입 여부와 이메일을 캐낼 수 있다.

---

## A6~A7 — 비밀번호 재설정

### A6 요청
- 이메일 입력 → "메일을 보냈습니다" 안내
- **가입되지 않은 이메일이어도 같은 안내를 보여준다** (열거 방지)
- M1에서 메일 발송은 콘솔 출력 (`MailSender` 인터페이스)

### A7 입력
- 토큰 링크로 진입. 새 비밀번호 + 확인
- 검증: 토큰 해시 일치 + 만료 전 + 미사용
- 성공 시 `usedAt` 기록 → 같은 링크 재사용 불가

## R1 — 동네 선택

- 서울 강북구 행정동 목록에서 선택 (GPS 사용하지 않음)
- 가입 직후 필수 진입

## R2 — 내 동네 관리

- 등록된 동네 표시, 추가/삭제, **지금 볼 동네 전환**
- **최대 2개.** 2개인 상태에서 추가하려 하면 안내
- 활성 동네는 서버에 저장하지 않고 요청 파라미터로 전달

## P1 — 상품 목록

**헤더**: 활성 동네 이름 (탭하면 R2로)

**카드에 표시할 것**
- 대표 이미지 (`sort_order = 0`)
- 상태 뱃지 (판매중 / 예약중 / 거래완료)
- 제목
- 가격 — `0`이면 "나눔"
- **판매자 닉네임**
- 동네 + 등록 시각 상대 표기 ("수유1동 · 3분 전")

**거래완료 처리**: 썸네일에 흰색 레이어를 덮고 가격을 muted로 — 목록에서 뒤로 물러나게

**조회 조건**
- 활성 동네(`region_id`) + `deleted_at IS NULL`
- 정렬: 최신순(`created_at DESC`) / 가격 낮은순 / 가격 높은순
- 검색: 제목 `LIKE` (M1 한정)
- 페이징: **`OFFSET` 방식**

**빈 상태**: "찾는 물건이 없네요"

### 이 화면의 성능 실험 포인트

| 항목 | M1에서 | 나중에 |
|---|---|---|
| 판매자 닉네임 | **N+1 발생하는 채로 둔다** | fetch join / `@BatchSize` |
| 대표 이미지 | **N+1 발생하는 채로 둔다** | 위와 동일 |
| 페이징 | `OFFSET` | 뒷페이지 지연 측정 후 커서 방식 |
| 검색 | `LIKE` | Elasticsearch |
| 인덱스 | **없이 시작** | `(region_id, status, deleted_at, created_at DESC)` |

**일부러 최적화하지 않는다.** mock 20만 건에서 느려지는 것을 먼저 측정해야
before/after 비교가 성립한다. 전역 지침의 "N+1 점검" 규칙은 이 프로젝트 M1에서 적용하지 않는다.
→ 프로젝트 `CLAUDE.md`에 예외를 명시할 것.

## P2 — 상품 상세

**상품 영역**
- 이미지 여러 장 (순서대로)
- 제목, 가격, 설명, 상태, 동네, 등록 시각

**판매자 영역**
- 닉네임
- 동네
- **판매 상품 수** — `ON_SALE`만 집계, 삭제된 것 제외

**판매자의 다른 상품**
- 최대 **4개**, 최신순
- 지금 보고 있는 상품 제외, 삭제된 것 제외

**본인 상품일 때**: 수정 / 삭제 버튼 노출
- 거래완료 상품은 수정 버튼 비활성
- 예약중 상품은 삭제 버튼 비활성 ("예약을 먼저 취소해주세요")

**쿼리가 4~5개로 늘어난다** (상품 / 이미지 / 판매자 / 판매 상품 수 / 다른 상품).
상세는 목록만큼 호출이 잦지 않으므로 M1에서는 나눠 조회해도 무방하다.

---

## P3 — 상품 등록

**입력**
- 이미지 업로드 (최대 10장, 순서 지정)
- 제목 (1~100자)
- 카테고리 (선택)
- 가격 (0 이상 1억 이하, `0`이면 나눔)
- 설명 (1~2000자)

**동네는 입력받지 않는다.** **지금 보고 있는 동네로 자동 지정**한다.

**이미지 업로드 (M1)**
- **로컬 디스크 저장만.** S3는 나중 단계
- `ImageStorage` 인터페이스 뒤에 둔다
- 검증: 크기 상한, 확장자 허용 목록, **실제 이미지인지 확인**(확장자만 바꾼 실행 파일 차단), 파일명 충돌 방지
- 저장된 파일은 `/images/{...}` 형태 URL로 내려준다 (mock의 외부 URL과 화면에서 동일하게 처리)

---

## P4 — 상품 수정

P3와 같은 폼에 기존 값이 채워진 상태.

**제약**
- 판매자 본인만 (타인은 403)
- **거래완료 상품은 수정 불가**
- 동네는 변경할 수 없다 (등록 시점 고정)

## 공통 사항

### 반응형
디자인이 모바일 기준이다. 데스크톱은 컨테이너 `max-width: 1120px`,
카드 그리드 `repeat(auto-fill, minmax(220px, 1fr))`, 하단 탭바 대신 상단 헤더.

### SSR(web 모듈) 구현 시
- 디자인 HTML은 Vue 스타일 `{{ }}` 템플릿이다. `th:text`, `th:each`, `th:field`, `th:errors`로 옮긴다
- 폼 제출 후에는 **PRG 패턴**(Post-Redirect-Get)을 쓴다. 새로고침 시 중복 제출 방지
- CSRF 토큰은 모든 폼에 포함
- 스타일 작업은 **기능이 다 동작한 뒤 맨 마지막에 별도 커밋**으로 한다

### M1에서 만들지 않는 화면
채팅, 거래(예약/구매확정), AI 등록, 알림, 마이페이지, 범위 설정
